1. The app in one paragraph

Zajel is an offline, ad-free file-transfer app for Android (iOS and desktop come later), Arabic-first (RTL) with English. It is wire-compatible with the LocalSend v2.1 protocol (https://github.com/localsend/protocol) and adds optional "Zajel extensions" (parallel chunked upload, tar bundles for many small files, a native Kotlin data path) that are negotiated by HTTP headers, so stock LocalSend apps still work. Flutter 3.38 / Dart 3.10, Riverpod 3, go_router, freezed, Pigeon for all native calls, minSdk 26. About 9,700 lines of Dart, 2,400 of Kotlin, 4,800 of tests (325 tests, all passing; flutter analyze clean).

Hard rules (from CLAUDE.md — do not suggest breaking them)

  • All transfers use TLS (self-signed certificate per device, identity = SHA-256 fingerprint of the DER certificate). The only plain-HTTP thing is the optional browser share page, which warns the user.
  • No ads, no analytics, no network calls to any server. Libraries that bundle telemetry (e.g. Google ML Kit) are forbidden; an automated test scans manifest, pubspec, Dart code and every plugin's Gradle files.
  • Native code is reached only through Pigeon (no raw MethodChannel strings). On Android the file bytes never pass through Dart on the fast path: Kotlin writes with FileChannel; never load a whole file into memory.
  • Received file names are sanitised (no .., absolute paths, control characters). No exported FileProvider.
  • Colors only through ThemeData tokens; all user-visible strings through ARB files (lib/l10n/app_ar.arb is the template).

Life of a transfer (Zajel → Zajel, big file)

  1. Sender: POST /prepare-upload with file list and header x-zajel-extension.
  2. Receiver (_prepareUpload): calls onIncoming → UI dialog (accept/decline, 60 s). On accept it creates _Session, emits SessionStarted, starts the idle timer (sessionIdleTimeout = 2 min, reset by _touch()), reserves a .zajel-part file per file, registers each with the native server, answers with session id, per-file tokens, x-zajel-data-port.
  3. IncomingTransferHost (after the dialog closes with "accepted") calls GoRouter.go('/receive'). Meanwhile the sender has navigated to its own progress screen.
  4. Sender uploads 8 MiB chunks over 4 TLS connections to the data port. Kotlin writes each chunk to disk, then onNativeChunk(sessionId, fileId, offset, length) → Dart _commitChunk records the range in a RangeSet, emits FileProgress; when the set is complete it renames the part file and emits FileReceived.
  5. When every file is done: SessionEnded(cancelled:false). ReceiveTracker meanwhile calls publishFile per finished file (MediaStore copy, then deletes the private copy).

5. The open bug — exactly what we know

User report (verbatim, Arabic): «ولا مشكلة الا مشكلة شاشة الاستقبال عند الطرف الاخر و برضو فيها مشكلة لمن تفتح الشاشة ما ببين تقدم بس بضل 0% و بعد كم ثانية بطفي عند الطرفين»

Translation: "No problem except the receiving screen on the other device. Also it has a problem: when the screen opens it shows no progress, it just stays at 0%, and after a few seconds it turns off on both devices." (The same user confirmed that files do arrive and appear in the file manager.)

Facts

  • Files do arrive and are published to the public folder, so the transfer itself completes at least in some runs.
  • We do not know the file sizes used, whether the link was the 1 MB/s router path or the 30 MB/s QR path, or what "turns off" looked like (screen leaves to Home? turns into the "done" state? the whole phone screen sleeps? an error card?). We have no log from that run. The app has Settings → export log; adb logcat -s ZajelWifi flutter would also help.
  • Before the round-2 build, the receiver had no receiving screen at all, so this is the first time anyone looked at receiver-side progress.

Hypotheses, most likely first

#HypothesisEvidence / reasoning
H1Receiver progress is chunk-granular on the native path. Kotlin only tells Dart when a whole 8 MiB chunk is on disk. With 4 parallel chunks, a file ≤ 32 MiB shows 0% until all its chunks land at once, then jumps to 100% and the session ends → screens change within seconds.Read directly from _commitChunk / NativeDataServer.serveOne; matches "0%… then gone". The sender's own bar moves because it counts bytes handed to its socket. Fix written (section 6).
H2Idle timer aborts slow transfers. _touch() was only called from Dart-side events, i.e. once per committed chunk. On a slow link (e.g. 100–300 KB/s) one 8 MiB chunk can take more than the 2-minute sessionIdleTimeout; _abortSession(cancelled:true) then ends the session on the receiver, and the sender's next request gets 403 / fails → both screens end.Code reading. Would not be "a few seconds" unless the link is very slow, so H1 explains the symptom better; H2 is a real latent bug either way. Fix written (progress callbacks now call _touch()).
H3Event-stream race. receiveSnapshotProvider is yield service.receive.current; yield* service.receive.stream; on a broadcast stream. Events emitted in the tiny gap between the two are lost, which could leave the screen stale.Window is microseconds; low probability, but trivially removable by emitting the current value on subscribe. Fixed (section 6).
H4Android lifecycle. The receiver app is in the foreground but the foreground service (FOREGROUND_SERVICE_DATA_SYNC) could fail to start on Android 14+ (type/permission/notification permission denied), or the sender's Dart isolate could be throttled when its screen turns off.No evidence; the phones' Android versions were not recorded. beginTransfer swallows exceptions from startTransferService.
H5Sender cancels. Any exception in SendJobNotifier.send shows an error card (not "closing"), but cancel() resets state to SendJob() and the screen returns Home. A cancel from the sender would show "cancelled" on the receiver.No evidence.
H6Publish step. ReceiveTracker._save awaits Kotlin publishFile (copy to MediaStore, delete source). If it throws or is slow, the file stays "saving" and the session end waits (isOver needs no file in saving).User says files appear in the file manager, so publishing works at least for them.

6. Changes made after commit af7b01c

  • Live receive progress. Pigeon NativeDataCallbacks.onNativeProgress(sessionId, fileId, liveBytes). Kotlin keeps an AtomicLong live per upload, adds every buffer it writes, reports at most every 200 ms, and subtracts the chunk once it is fully written (just before asking Dart about the chunk). Dart _onNativeProgress emits FileProgress(covered + liveBytes) and calls _touch().
  • ReceiveTracker makes the receiving bar monotonic (between "chunk written" and "chunk committed" the two numbers are briefly out of step).
  • Test added: with the fake native bridge, progress values strictly between 0 and one chunk size are seen and never decrease. All 325 tests pass; the Kotlin changes compile but have not run on a phone.
  • receiveSnapshotProvider now subscribes to the tracker stream before adding the current value (H3).
  • One extra log line when a file is received.

8. What we would like from you

  1. Read sections 2 and 4 and the listed code. Find a cause of "0% then both screens end" that we have not listed, or confirm H1/H2 and say what else would be needed to make the receive screen trustworthy.
  2. Review NativeDataServer.serveOne and ReceiveServer._onNativeChunk/_onNativeProgress for races or leaks (live-byte accounting when a connection drops mid-chunk, a retried chunk, two connections writing different chunks of one file).
  3. Review the session lifecycle (_touch, _abortSession, _endSessionIfFinished, PendingIncoming 60 s timeout, IncomingTransferHost navigation) for a path that ends the session or the screen early.
  4. Suggest the smallest instrumentation (log lines or on-screen debug text) that would make the next phone test conclusive, given that we can only ask the user to send an exported log.
  5. Any Android-specific pitfalls you know for: foreground service type dataSync on Android 14/15, MediaStore publishing from a background thread, WifiNetworkSpecifier + bindProcessToNetwork, Wi-Fi Direct DNS-SD discovery (we call discoverPeers plus repeated discoverServices every 4 s).
